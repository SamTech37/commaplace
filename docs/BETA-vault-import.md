# 資料夾匯入 Beta · 2026-09-05

目的：Hank 親自匯入大量筆記，觀察網站發生的好事與壞事。先有完整可用的 beta，再用實際結果決定產品規則。

## 尚未定案的三個問題

1. 舊文章在個人時間軸回到歷史位置，還是算今天發布？公共 feed 是否改成「某人匯入 800 篇」的批次入口？
2. 真實 vault 的可信寫作日期是 frontmatter `date` / `created`、檔名日期，還是檔案 mtime？用實際檔案驗證，不推測。
3. 整個 vault 是否真的都願意公開？**已依 Hank 實測修正：必須逐檔可見、可預覽、可勾選，預設全部不勾選。** 支援直接選取 Markdown 檔案，或從資料夾清單排除私人筆記。

上述是問題，不是已拍板的功能。本版沿用匯入當下的 created_at / updated_at / published_at；原始 frontmatter（含日期及自訂屬性）保留於 Markdown，閱讀頁不顯示 YAML。mtime 尚未匯入。不用原始日期代替複合游標修正。

## 使用

書寫頁「已儲存」左側 → **匯入筆記 Beta** → 選取 Markdown 檔案或資料夾 → 搜尋路徑、查看本機原文、勾選要公開的檔案 → **發布勾選的 N 篇**。預設全不勾選；選取與預覽都不會上傳。只有勾選的檔案會放入請求，未勾選內容不會傳到伺服器。當前正在寫的草稿不會被替換。

清單每頁 100 檔；「勾選搜尋結果」會選取所有符合搜尋的檔案（含其他頁），「全部取消勾選」清空所有頁的選取。切換來源會重置勾選。直接多選檔案不提供原始資料夾路徑；若要保留跨資料夾連結，請用資料夾入口，再從清單勾選。相同檔名的直接多選會阻擋上傳，避免路徑混淆。

- 遞迴上傳 `.md`（大小寫皆可）；跳過非 Markdown 與任何以 `.` 開頭的檔案或資料夾，包括 `.obsidian` / `.trash`。
- 一次最多 2,000 篇、HTTP 請求 100 MiB、每篇 2 MiB。前端內容上限 99 MiB，預留 multipart 標頭空間。UTF-8；不收 ZIP。
- 保留目前網站支援的 Markdown、callout、task list、表格、highlight、數學、註解、Wiki 別名、標題錨點、筆記嵌入與超連結。這不等於執行 Obsidian 外掛；Dataview、Canvas、區塊引用等原有 renderer 未支援的功能仍待驗證。
- 沿用 `StripMedia`，移除圖片、影片、音訊；附件不儲存。
- 以檔名產生網址，title frontmatter / H1 作顯示標題。同名網址自動加 `-2` 等後綴；不覆寫既有筆記。
- 連結對應順序：明確相對路徑、vault 根目錄路徑、同資料夾檔名、全 vault 唯一檔名。跨作者 `@handle` 連結保留。無法判斷的同名 Wiki 連結留為未解析，並記錄警告，避免錯接到別人的同名檔案。
- `.md` 格式的普通相對 Markdown 連結會轉成站內 Wiki 連結。參考式連結、複雜巢狀連結、僅使用 frontmatter aliases 的尋址尚需真實 vault 驗證。
- 先建立整批筆記，再解析連結，最後一次交易提交。失敗回復整批；成功紀錄與筆記同時提交。同一批次按「重試」不會重複匯入；重新選取並開始新的批次則會新增一份，不是同步更新。
- 伺服器逐檔暫存並刪除暫存檔；最多同時處理兩批、每位作者串行；五分鐘逾時。沒有新增雲端服務或提高資料庫方案。
- 完成後顯示發布篇數、移除媒體數、未解析連結數，並可下載完整 JSON 報告（每篇原路徑、新網址、警告、ID）。畫面最多展開 100 篇。
- 同一分頁重新整理後，重選並勾選同一組檔案可接續尚未收到成功回應的批次；選取的子集合變更會建立新批次，不會自動帶回先前的私人檔案。瀏覽器禁止 sessionStorage 時，跨重新整理的批次恢復不可用。

### 測試資料

`python scripts/make-beta-vault.py <不存在的新資料夾>` 產生 800 篇、日期與 mtime 分布 2023–2025 的測試筆記，有環狀跨資料夾連結及多種 Markdown。腳本拒絕覆寫既有資料夾。這版網站仍按匯入時間排序，日期分布用來檢視下一版的時間政策。

### 已自動驗證

- `node --test scripts/vault-import-ui.test.cjs`：預設不勾選、本機預覽不發請求、取消勾選的模擬私人檔案不出現在 multipart、直接多選檔名、跨頁搜尋勾選、來源切換重置、同名阻擋。

- 800 篇發布、800 個批次內連結解析、同秒 profile 40 頁全部可達；相同批次重試不增加筆記。
- Profile、tag、saved、following 同秒分頁不漏、不重複。
- 超過預設 multipart 1,000 part 限制的 1,001 檔匯入讀取。
- 路徑／編碼／檔案大小驗證、YAML 清單／日期／長行保留、同名網址、取消交易、未登入阻擋、gzip middleware 下的串流進度。

### Beta 實測抓到並修正的問題

第一次透過瀏覽器選資料夾上傳：800 篇成功、1,600 處媒體移除，但出現 800 個假的未解析連結。原因是既有 `markdown.Extract` 直接掃描字串，把程式碼區塊裡示範用的 `[[連結]]` 算入圖譜。已改用與閱讀頁相同的 Markdown parser，忽略程式碼、註解與 YAML，並新增回歸測試。

另補齊參考式圖片（`![alt][id]`、`![id]`）及巢狀括號圖片的清洗，普通參考式超連結與其定義保留。

Windows 產生的 CRLF 換行也讓舊的卡片摘要解析漏掉 frontmatter，將 YAML 印在時間軸。閱讀頁、摘要、卡片分類與標籤抽取現在共用支援 CRLF 的 frontmatter 分割，新增卡片回歸測試。

匯入前查看原文曾只顯示空灰框；現場 DOM 確認預覽文字長度為 0，但未據此判定使用者原檔是空的。現在顯示實際檔案大小，區分 0 B 空檔、只有空白、非空檔卻讀不到內容及讀取失敗；正常內容保留為本機純文字，不執行 HTML 或載入外部媒體。按鈕改為「查看原文」，展開後聚焦內容。新增空內容與非同步切換回歸測試，7 項前端測試通過；另以瀏覽器驗證正常中文 Markdown、空檔及空白檔。此功能是發布前的原文檢查，並非排版後的閱讀頁預覽。

修正後再次以瀏覽器選取同一份 800 篇、2023–2025 年測試資料：800 篇發布、1,600 處媒體移除、0 個未解析連結，本機資料庫處理 4,005 ms。桌面與 390px 手機寬度的按鈕及結果視窗已目視確認。此數字不含上傳，也不代表 Render 效能。

### 仍須實機觀察

- 本機測試的速度不是 Render 小方案的效能承諾；需記真實 vault 的檔案大小與連結密度。
- 公共 recommended feed 仍沿用每頁每作者最多三篇的排名方式；它不是完整 vault 清單。混合其他作者與大量舊文時，實際曝光是否合理尚待觀察。
- 全站圖譜、搜尋、tag 聚合在大量筆記後的可讀性與耗時。
- 重選／重新匯入同一個 vault 的產品政策；目前只有同一次請求重試去重，沒有同步或內容去重。
- 有效但網站未支援的 Obsidian 語法與媒體變體，逐項帶原始範例回報。
- 已觀察到：從書寫頁進入會先產生空草稿，因此個人頁可能顯示 801 entries（800 篇公開＋1 草稿）；報告的發布篇數是 800。
- 已觀察到：原文同時有 frontmatter title 與 `# H1` 時，筆記頁會顯示頁面標題與原文 H1 兩次。Beta 保留原文，後續再決定是否只在呈現層省略重複 H1。
